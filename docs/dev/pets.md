# Homepage pets

ARC bundles no pet artwork. The Pets sheet links to community packages and imports them through local management operations. Pets are a homepage topology decoration, above task bubbles. Sheets and panels cover them. Task bubbles retain information and task ownership.

## Packages and storage

A Codex Pets package contains `pet.json` and the single image named by `spritesheetPath`. The manifest requires a nonempty `id`. `displayName`, `description` and `spriteVersionNumber` are optional; a supplied version must match the image. Cells measure 192 × 208. V1 is 1536 × 1872 (8 × 9); v2 is 1536 × 2288 (8 × 11). Rows 0–8 are idle (6 frames), running right (8), running left (8), waving (4), jumping (5), failed (8), waiting (6), working (6), and review (6). V2 rows 9–10 contain sixteen look directions.

`pets.list`, `pets.asset`, `pets.install`, `pets.import`, and `pets.remove` are local management operations backed by Core. They do not extend control-source MCP tools or events. Core verifies HTTPS and exact download hosts, rejects redirects, caps transfer and expanded package bytes at 25 MB, decodes the atlas, and requires supported dimensions. ZIP files contain exactly two root files; paths, duplicates, directories and symlinks are rejected. Archives are read in memory and only validated files are written. The import HTTP body allows base64 overhead without changing other request limits.

For codex-pets.net, Core resolves the exact ID through the search API, downloads its ZIP, and compares the package with `validationReport`. For codexpet.top, Core uses the awesome-codex-pet install manifest and verifies both file sizes and SHA-256 digests before reading submission metadata. Other sites, including openpets.dev, use ZIP import. The publisher may update between requests; hash mismatch fails the installation without replacing installed files.

ARC stores content-addressed packages under its state directory's `pets/` folder using staged atomic renames. `source.json` records site, original page URL, author, license, attribution, file SHA-256 values and installation time. Missing publisher metadata stays missing. The sheet links to the original page without displaying author, license or attribution fields. Core also validates and lists `~/.codex/pets` read-only. Invalid local packages appear as errors. ARC never writes into the Codex directory.

## Binding and presentation

Show pets defaults off. `arc.pets.show` and `arc.pets.assignments` use existing Core-backed preferences. Selection resolves `source:<id>` or `agent:<id>` first, then the enclosing `platform:<id>` for either a control source or an Agent, then `default`. Without a valid global default, the first installed package by name and key is used. Missing packages fall through to the next enclosing scope. Internal brand defaults are no longer used and are discarded on the next assignment write. Sub-accounts share their Agent binding.

Platform, connector and Agent panel headers expose a paw button. Its Radix popover lists all installed packages through shared SingleChoice controls, as an image-only grid with accessible names, hover titles and an option to inherit the enclosing default. The inheritance option previews the resolved parent pet and clears only the current scope; it does not copy the current global default into that scope. Selection applies immediately to that scope. The Pets sheet manages installation, removal and the global default only. Community links, URL installation and ZIP import share one section. Installed packages use responsive cards with the preview on the left and three rows on the right: name, linked source domain or local origin, and actions. Manifest descriptions remain available as hover titles. Codex packages disclose their read-only constraint. Previews load only validated local atlases. Asset rights remain with original authors; the UI states personal, non-commercial use.

`pets.remove` resolves an opaque package key from the native library and only removes ARC-owned directories. The UI clears every assignment referencing the deleted package after removal succeeds. Codex packages cannot be removed by this operation or the sheet.

Topology owns anchor geometry in both orientations. Participant sprites use 96 × 104 cells (atlas scale 0.5); task sprites use 0.6 of that size (57.6 × 62.4). Sheet previews remain 72 × 78. Sprite frames, hit areas, drag bounds and card attachment coordinates share these dimensions. A fallback name tag fits inside the sprite width and adds 18 pixels to the hit area and collision footprint.

Participant posts prefer the side of their node facing the hub. The pure post solver excludes all visible node icons and measured label bounds, including wrapped portrait labels and account labels. It slides the post around obstacles or uses another side when necessary. If no safe post fits, the pet is hidden until space becomes available. This does not move topology nodes. Deliberate pointer dragging remains free within the scene bounds. Drag positions exist only in renderer memory, stay below the title strip and never reorder tasks. Clicking a pet selects one of sixteen localized reactions from a shuffled deck. Every reaction combines atlas rows with a gesture; the deck avoids repetition until exhausted. Task pets still open their task panel. Dragging starts only after deliberate pointer movement crosses the mouse or touch threshold; small movements still click. The final pointer-up coordinates are applied before release, and capture loss preserves the last dragged position. Dragging uses the waiting row. Releasing keeps the pet at the dropped position, without gravity. Task pets pause for two seconds, then walk back to their bubble through free space. Participant pets pause for twelve seconds, then resume walking from their current position. Resizing clamps positions within the scene. Escape or pointer cancellation restores the position and placement mode from before the drag. Task-driven speech is limited to one line per pair per 30 seconds. Explicit clicks always receive feedback.

Frame animation uses CSS `steps()`, with independent phase offsets and cadence for each pet. Role-specific poses follow the observed thinking, command, file, tool, text or interaction phase; pending input and failure keep their semantic rows. Poses vary every few seconds, so participant and task sprites do not mirror each other. Idle cadence slows when no task runs. Movement alone schedules animation frames. Hidden/minimized windows suspend motion and reduced motion uses static frames. Native visibility reads are limited to visibility/resize events. Assets are fetched once per renderer and shared by package key.

Participant pets choose short random walks within the visible scene. Walks avoid node labels, bubbles, the hub and other participant pets over their entire swept footprint. A blocked walk waits for another destination rather than moving through an obstacle. Hidden windows and reduced motion suspend walking and social encounters.

Visible source and Agent pets occasionally wave, exchange encouragement, or toss a decorative star back and forth. Social encounters wait while a pet is approaching or using a scene contact. The first encounter is eligible after eight seconds; subsequent encounters are spaced 24–42 seconds apart. Encounters pause walking, yield to task choreography and stop when either participant is dragged or clicked. They do not submit tasks or imply any execution result.

## Limits

No pet artwork, sound, package code, automatic pet downloads or persistent pet positions are included. Scene contact poses use existing atlas rows with restrained transforms; imported packages do not provide dedicated sitting or gripping frames. ZIPs with wrapper directories must be repackaged with the two files at the root. Local Codex packages with unsafe filenames or symlinks are unavailable. Packages whose previews have not loaded show a generic icon. Codex package deletion remains with the owning application.

## Relay choreography

`ui/pets/relay.ts` is a pure projection of unified execution states and observed transitions. `PetLayer` reads tracked activities, `taskExecutionModel`, resolved pending interactions and dispatch records. It matches each dispatch to the executing turn and uses `sourceId` for the source participant. Sub-accounts provide launch coordinates, never another pet identity. Task pet clicks call the same task-panel selection as the task bubble. Task anchors resolve the actual rendered task ID and use its animated width, height and left/right anchor to compute the bubble's bottom-right corner. Task pets dock across the right edge with their feet aligned to the bottom edge, in front of the bubble. Between task cues they choose random destinations around the bubble perimeter, pausing between walks. A visibility graph routes their full footprint around visible nodes, labels, the hub and other bubbles. A short escape or docking segment handles a dragged pet inside an obstacle or the deliberately overlapping bubble dock. Missing routes are retried without teleporting. Moving bubbles invalidate the current route; hidden bubbles suspend the pet. Click reactions, dragging and task relay cues take precedence over wandering. Hidden queue members anchor at their existing aggregate bubble. When a collapsed branch has no rendered bubble, its task pet is hidden until the bubble returns; it does not pile up on the Agent node. Pets never expand queues, rewrite task order or change execution state.

Stable intent identities deduplicate repeated observations. Dispatch waves and throws a card along a bounded arc; the Agent catches it. Flying and carried cards share the actual task title and a deterministic task color. Cards are visual tokens; full task bubbles keep their readable layout and task ownership. A new running turn creates a task pet beside the executing account node, carries a card to the bubble and uses working row 7. With reduced motion, task pets snap directly to their bubble destination and skip intermediate relay positions. Pending input uses waiting row 6; unknown evidence uses review row 8. A running phase lasting at least 90 seconds produces one urge intent for that phase. Terminal transitions hand the card from the task to the Agent and then back to the source, green for done and red for failed or interrupted. A pass review triggers a jump and thumbs-up; rework sends the card to the Agent again. Unavailable review reads never alter execution evidence. Reviews are read through the existing local endpoint every 15 seconds while pets are enabled, the window is visible and terminal tasks remain tracked; no review or task writes occur.

The resident source and Agent come from the same observed Loop. Pending input takes priority over running work, then unknown and terminal work. A resident pair remains stable among equal-priority tasks; unrelated source activity cannot replace half of a pair. Only confirmed dispatch records can establish historical pairs. Missing source attribution does not manufacture a partner; native work can show its Agent alone. Relay episodes from another Loop temporarily present both of its participants together, with different pairs serialized to keep handoffs attributable. Native task timestamps and confirmed dispatch records establish recency; polling time and topology order do not. Observed clocks remain in renderer memory after completed bubbles disappear. Revoked and pending sources and disabled Agents are excluded. Only these two participants receive main pets; task pets leave after 60 seconds idle, with a two-second return period. Participant name tags display the full name without ellipsis. Task pets have no independent population cap; existing activity retention still determines available tasks. Both task and participant placements temporarily defer autonomous walking. Neither is persisted across renderer recreation or pet removal. Reduced motion disables wandering and gestures while preserving held and manually placed pets, including after release; click text remains available. Task-driven speech cooldown is shared by the source/Agent pair; deliberate click feedback and occasional social replies use their own durations.

`app.snapshot.model.pets` reports `petCount`, `animatedPetCount`, `taskPetCount` and `movingCardCount`. Counts describe mounted pets with available assets and anchors. Hidden or minimized windows and reduced motion report zero animated pets. CSS owns atlas frames and contact poses; animation frames run only for moving pets, flying cards or a bounded icon tug. Discrete choreography boundaries use timeouts. The atlas must be static PNG or WebP so intrinsic file animation cannot bypass visibility and reduced-motion controls.

Browser scenarios are `pets-idle`, `pets-relay`, `pets-done`, `pets-failed`, `pets-dragged`, `pets-waiting`, `pets-settings` and `pets-subagents`. The subagent scenario includes a parent, children and a grandchild with distinct execution phases, plus overflow and an independent task. Fixture code generates geometric v1/v2 atlases on a canvas and supplies local in-memory package metadata. The dragged fixture starts a participant in a displaced drag state with the waiting row, preserved with motion enabled or reduced; the production pointer handlers remain available for later interaction checks. Fixtures are development-only and include no third-party artwork. They support later browser acceptance in both topology orientations; native minimization and real downloads require separate explicit runtime verification.

## Pixel-art rendering

Core computes `pixelArt` from the decoded static atlas during validation. The version 1 heuristic counts exact RGBA colors among pixels with nonzero alpha. A nonempty palette of at most 256 colors is pixel art; a larger palette or an entirely transparent atlas is not. RGB values of fully transparent pixels do not contribute. The palette set stops growing at 257 entries. The result is deterministic and does not depend on a package name, site or frame order.

ARC stores the result and `heuristicVersion: 1` in `rendering.json` beside newly installed packages, and refreshes this file on explicit reinstall. Package listing returns the freshly validated `pixelArt` value for both existing ARC packages and read-only Codex packages, so older installs do not need a write migration. No file in the Codex pets directory is changed. The renderer applies `image-rendering: pixelated` to classified packages in both the homepage and sheet previews; other packages use normal interpolation. The heuristic can classify low-color illustrations as pixel art and miss pixel art with large or antialiased palettes. It is a rendering hint, not an installation restriction.

## Scene contacts

Topology provides contact points for the hub rim, connector curves and participant icons in both orientations. A participant occasionally walks to an unoccupied contact, then perches, swings or tugs before returning to wandering. Pets leaving an overlapping hub contact use an obstacle-aware departure route. A moved contact with no valid route cancels the approach. Contacts yield to explicit dragging, reactions, task relay and pending input. Open panels, topology dragging, unavailable anchors and layout transitions cancel unavailable contacts. A tug applies only temporary visual displacement to the icon; it does not reorder nodes, activate controls or change connectivity. Displacement is cleared on cancellation, hiding, removal and unmount.

Scene contacts are positioned from current topology geometry. Sitting uses a seat point at 73 percent of sprite height; swinging rotates around a grip near 28 percent of sprite height. These are generic poses for existing v1/v2 atlases, not synthesized limb animation. Hidden windows and reduced motion suppress contact choreography.

Development pet scenarios accept `petAction=sit`, `petAction=swing` or `petAction=pull` to display a contact directly for browser acceptance. The parameter is ignored outside development scenarios and is not a persisted preference or production control.
