# Loop 效率：实现/验收拆分（实验）

> 状态：实验中。第一阶段（纯 Codex 拆分）由控制源按本文与用户 dispatch-policy criteria 执行；多 Agent / 多模型协作只作为 TODO 记录，不进产品。

## 动机：数据

2026-10-18 ~ 10-21，client（scnet-client / sacp-client）中 131 个 Codex 轮次，其中 ≥30 分钟的 16 个、共 22.8 小时（按 rollout 时间戳统计，每次工具调用前的模型时间 + 工具执行时间归入该调用的类别，脚本见 `scripts/dev/rollout-profile.py`）：

| 类别 | 占比 |
| --- | --- |
| 写代码 | 11% |
| 读代码/搜索 | 26% |
| 视觉验收（截图、对标采集、像素比对） | 25% |
| 等待/轮询（279 次 sleep 20s、132 次 write_stdin 空读） | 21% |
| 检查/测试/构建 | 10% |
| 上下文压缩 | 7% |

工具本身执行只占墙钟 14%，其余是模型逐步推理。慢的不是命令，而是用最高推理档（astra high）去执行大量确定性步骤。长任务几乎都被验收与等待拖长，很少是写代码写得久。

## 第一阶段：纯 Codex 拆分（进行中）

一个任务段拆成两个轮次，由控制源串联：

**实现轮**（gpt-6-astra，high）：高复杂度、关键决策、需要编码智能的部分。
- 控制源在 prompt 里给出要改的文件清单、规格和关键片段，减少探索式读代码。
- 只做实现 + 相关单测；结束前跑一次快速检查（类型检查 + 相关单测）。
- 不截图、不跑长流程（实跑、对标采集）、不 sleep 轮询、不写验收文档；每批改动一个提交。
- 单轮预计超过约 40 分钟就拆段。

**验收轮**（gpt-5.6-sol，medium，Fast）：不需要高智能的杂项。
- 新开线程（不带实现轮的长上下文），控制源给出验收包：提交范围、验收点、要跑的命令、要截的场景、证据存放位置。
- 跑全量检查、截图/采集、长流程；输出结构化报告：每项「通过/失败 + 证据（命令输出摘要或文件路径）」。
- 机械性失败（类型/lint、文案、明确的样式数值）可直接修并单独提交；语义或设计问题只报告，不改。
- 截图等二进制证据只留本地，不提交。

**控制源**：看报告与关键截图→通过；或把语义问题打包成精确失败清单，回到 astra 实现线程返工；下一段实现可以在验收轮进行时先派出（同一目录不并行改代码：验收轮只在有机械修复时提交，实现轮与之冲突时串行）。

**衡量**：每段完成后用 `scripts/dev/rollout-profile.py` 统计两个线程，对比写代码占比、总耗时与返工次数（派发历史的 pass/rework）。
