# Shared fallback on independent dispatch

**private-failure (D4)** — In the [installed setup](../installed.md) keep main closed and check independent recovery, the healthy shared daemon and native login. Run fresh trials for (1) launch denied before private readiness and (2) an existing private backend that accepts a connection but never answers readiness. Use a host-scoped fault confined to the identified private process or its private endpoint. For the timeout, suspend only the verified idle private PID and resume that same identity on cleanup. For startup denial use an isolated launch-denial fixture limited to the private executable or endpoint. If both routes use the same binary, a blanket deny fails the healthy-shared precondition. Record the actual error/timeout and continued successful shared control operation. No main Desktop, pending approval or first-turn submission may precede the fault.

Dispatch once with a unique marker. Resolve the original receipt and open its task detail. Remove the fault, verify health, and dispatch a new marker through the recovered private route.

**dispatched** — For the faulted request, the shared backend holds the original thread's writer while it runs, and native history on that ID contains exactly one accepted marker and a completed reply. Check for duplicate conversations after recovery.

**route-shown** — The resolved receipt and the matching task detail each identify the shared background and give a reason consistent with the injected startup failure or timeout. Capture the two surfaces separately.

Baseline expectation: shared routing exists before this change; a shared receipt without evidence of an attempted private dispatch cannot exercise fallback. Startup-denial coverage requires a private-only fault seam.
